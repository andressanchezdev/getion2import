Cómo leer el modelo. Se genera desde el script (pestaña 3), así que siempre coinciden. Cada grupo se dibuja de izquierda a derecha: a la izquierda las tablas de las que dependen las demás y a la derecha las que dependen de ellas. Cada flecha une dos tablas y va en una sola dirección: sale de la tabla referenciada y llega a la que guarda la llave foránea (FK). Las FK hacia otros grupos no se dibujan: están escritas dentro de cada caja, marcadas con ↗. Haz clic en una tabla para ver sus relaciones. Los mismos diagramas, página por página, están en el PDF diagrama_ER_V3_horizontal_claro.pdf de esta carpeta.

Cómo quedará la raíz completa de GestionImportadora y del frontend appImportadoraIp. La estructura por capas se conserva; solo se ajustan los archivos de estilo y de conexión, y se agregan los módulos nuevos. Cada carpeta de una feature sigue el orden types → helpers → services → slices → thunks → hooks → components → screens. El «panel derecho» y los «tres componentes» siguen siendo los de app/componentApp: los modos nuevos del panel son archivos de sus features, registrados en drawerRegistry.ts.

  
El frontend no depende de la API: capas y contrato

  
Si cambias la URL base, la API o la base de datos, las pantallas y los modelos del frontend siguen funcionando. Esto ya existe en Gestión Importadora (rutas en api/config.ts, tipos *.api.types separados de los modelos, *.adapter.ts) y V3 lo refuerza: los cambios del backend se absorben en una sola capa.

Cómo se hace cumplir: (1) una regla de ESLint impide que una pantalla o un componente importe un *.api.types; (2) solo los *.service.ts pueden importar api/client; (3) cada adaptador tiene su prueba con una respuesta de ejemplo, así un cambio del backend falla en la prueba antes que en pantalla; (4) npm run check:api compara las rutas de config.ts con el openapi.yaml de la API en Go.

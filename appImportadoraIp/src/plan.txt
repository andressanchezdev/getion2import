1. REGLAS INNEGOCIABLES DE ARQUITECTURA Y ESTRUCTURA DE CÓDIGO
====================================================================================================

1.1. Inviolabilidad de la Raíz de "src":
   No se crearán carpetas nuevas en la raíz de src/. Toda la solución se organiza exclusivamente en:
   - src/api/               -> Cliente Axios, configuración de URLs y endpoints maestros (src/api/config.ts).
   - src/app/               -> Montaje (main.tsx, App.tsx), Layout y Contenedores Padre (componentApp).
   - src/assets/            -> Iconos SVG y recursos gráficos estáticos.
   - src/features/          -> Módulos de dominio de negocio (cada feature contiene types, constants, helpers, services, slices, thunks, components, screens).
   - src/global/            -> Utilidades transversales (hooks, helpers, UI atoms, UI molecules).
   - src/styles/            -> Tokens CSS y variables de diseño (tokens.css).

1.2. Contenedores Padre en "componentApp" (Intocables):
   Los componentes en src/app/componentApp son los dueños de la interfaz visual general:
   - MainContent.tsx        -> Lienzo principal donde se renderiza la pantalla activa según activeModule y activeSubitem.
   - SideMenu.tsx           -> Menú de navegación lateral (consume MENU_ITEMS).
   - AppHeader.tsx          -> Barra superior (Logo corporativo, WarehouseSelector, botón Configuración).
   - DrawerRight.tsx        -> Panel lateral deslizable para carritos, auditorías y formularios contextuales.
   REGLA ESTRICTA: Ningún feature creará nuevos envolventes de layout ni duplicará estos componentes. Las pantallas de negocio se construyen como hijos en src/features/{feature}/screens/ y se inyectan a través del registro central src/app/componentApp/contentMain/screenRegistry.ts.

1.3. Criterio de Reutilización Global vs. Específico:
   - Si un componente visual (tabla genérica, modal, badge, chip de filtro, input validado) se utiliza en más de un módulo, DEBE residir en src/global/components/UI/.
   - Si un componente responde a una lógica 100% interna de un módulo (ej. calculador de billetes en Caja), reside en src/features/{feature}/components/.

1.4. Política de Cero Duplicación de CSS:
   Se prohíbe duplicar reglas CSS. Todo estilo utiliza los tokens semánticos de src/styles/tokens.css (colores, espaciados, radios, tipografías, transiciones).

1.5. Política de Depuración de Archivos:
   El agente bajo NINGUNA circunstancia eliminará archivos o carpetas directamente. Cualquier archivo obsoleto o mock antiguo se documenta en la Sección 13 para que el Desarrollador Senior / Scrum Master ejecute la eliminación manual.

1.6. Usuarios del ERP = Exclusivamente Empleados de la Empresa:
   Clientes, proveedores y transportadoras son directorios maestros de datos administrados por el personal. Quienes tienen credenciales de acceso, inician sesión y ejecutan acciones auditadas son única y exclusivamente los empleados de la empresa.

2. IDENTIDAD DEL EMPLEADO Y FIJACIÓN AUTOMÁTICA DE BODEGA AL LOGIN (POST /auth/login)
====================================================================================================

2.1. Contrato Exacto de Swagger:
   - Endpoint: POST /auth/login
   - Request Body: models.LoginRequest
     * email (string, requerido)
     * password (string, requerido)
   - Response: response.APIResponse donde data es models.LoginResponse:
     * access_token (string)
     * refresh_token (string)
     * user: models.UserResponse conteniendo:
       - userId (integer)
       - companyId (integer)
       - warehouseId (integer) -> Bodega física asignada por defecto al empleado
       - name (string), lastName (string), email (string)
       - userType (string) -> 'admin', 'seller', 'cashier', 'warehouseman', etc.
       - priceType (string) -> Tarifa predeterminada
       - identification (string)
       - comissionRate (number)
       - photo (string)
       - companyInformation (models.CompanyDetails)

2.2. Diagnóstico del Problema Actual:
   Actualmente, el helper pickActiveWarehouse en src/features/warehouses/helpers/warehouses.helpers.ts le da prioridad a la bodega almacenada en el estado local persistido (currentId) por encima del userWarehouseId retornado en el login. Esto provoca que un empleado asignado a la "Sede Norte" inicie sesión y quede ubicado en la bodega de una sesión previa ajena ("Sede Principal"), visualizando existencias de otra sede.

2.3. Solución Técnica Implementada en Código:
   1. En el thunk de inicio de sesión (src/features/auth/thunks/auth.thunks.ts -> loginThunk):
      Al resolverse POST /auth/login con éxito, se extrae response.data.user.warehouseId y se despacha inmediatamente la acción Redux:
      dispatch(setActiveWarehouse({ id: String(response.data.user.warehouseId), name: 'Sede Asignada...' }));
   2. En src/features/warehouses/helpers/warehouses.helpers.ts -> pickActiveWarehouse:
      Se reestructura la prioridad:
      - Si el empleado tiene userWarehouseId asignado y su rol NO es superadmin multisede (userType !== 'admin'), se fuerzan SIEMPRE los datos de su sede física.
      - Si el empleado es superadmin (userType === 'admin'), se permite la alternancia libre de bodegas.
   3. En src/app/componentApp/header/warehouse/WarehouseSelector.tsx:
      Si el usuario no cuenta con permiso multisede, el selector se desactiva visualmente (renderiza en modo lectura fija como badge no interactivo), impidiendo que el cajero o vendedor opere sobre bodegas ajenas.

2.4. Carga e Hidratación del Árbol de Permisos en Sesión:
   Al resolverse POST /auth/login con éxito:
   - Si response.data.user.userType === 'admin' (Superadministrador):
     Posee bypass maestro total. Todos los módulos, subítems y botones de acción se habilitan sin restricción en toda la aplicación.
   - Si response.data.user.userType !== 'admin' (Empleado operativo: cajero, vendedor, bodeguero):
     El sistema despacha inmediatamente POST /employees/permissions enviando { employeeId: response.data.user.userId }.
     La respuesta (models.EmployeePermissionsResponse) hidrata el estado global en Redux (state.auth.permissions), gobernando qué módulos y subítems se renderizan en el Menú Lateral (SideMenu) y qué acciones CRUD (crear, editar, eliminar) se permiten en cada pantalla.

3. EJE CENTRAL DE STOCK: EL FÍSICO MANDA (POST /products, models.ProductLocation Y WEBSOCKETS)
====================================================================================================

3.1. Contrato Exacto de Stock en Swagger:
   - Endpoint: POST /products
   - Request Body: models.GetProductRequest
     * companyId (integer, requerido)
     * warehouseId (integer, opcional: filtra locations por bodega específica)
     * hasStock (boolean, opcional: true = locations con stock > 0)
     * isActive (boolean, opcional: default true)
     * isPromotion (boolean, opcional)
     * brandIds (Array[integer], opcional)
     * categoryIds (Array[integer], opcional)
     * modelIds (Array[integer], opcional)
     * familyIds (Array[integer], opcional)
     * page (integer), pageSize (integer)
   - Response: response.APIResponse donde data es Array[models.ProductResponse].
     Cada producto contiene:
     * locations: Array[models.ProductLocation]:
       - productLocationId (integer)
       - productId (integer)
       - warehouseId (integer)
       - locationCode (string)
       - stock (integer)         -> Existencia física total en estantería
       - reservedStock (integer) -> Existencia virtual comprometida en carritos activos y pedidos en picking
     * prices: Array[models.ProductPrices]:
       - productPriceId (integer)
       - productId (integer)
       - type (string)          -> Nombre o etiqueta de la tarifa (ej. "DETAL", "MAYORISTA", "TALLER")
       - price (number)         -> Valor monetario unitario
     * models: Array[string]    -> Lista de modelos de motocicleta compatibles
     * modelName: string        -> Modelo principal
     * code: string             -> Referencia SKU
     * description: string
     * brandName (string), categoryName (string), brandImage (string)

3.2. Fórmula Matemática de Stock en Frontend:
   Para cualquier bodega evaluada:
   - Stock Físico Real =campo devuelto por la api, con stock de el producto, y debe tambien devolver la cantidad de ese producto de forma virtual, el campo como cantidadAux, o algo similar 
   - Stock Virtual = campo devuelto en la respueta de la api que representa las cantidades virtuales
   - Stock Físico Disponible para Venta = location.stock - location.reservedStock


3.3. Mecanismo de Bloqueo Inmediato:
   - Si Stock virtual es pedido full cantidades y esto cubre la cantidad fisica disponible entonces agotado== cantidad virtual == a cantidad fisica entonces agotado = 1, el botón "+ Agregar al carrito" en ProductCardActions.tsx se deshabilita automáticamente y muestra badge "Agotado en Bodega".
   - Si un vendedor agrega unidades a un carrito, se descuentan en vivo del Stock Disponible.
   - En caso de agotamiento de stock físico, el backend vía WebSocket (VITE_WS_URL) notifica el evento 'stock_updated', bloqueando la tarjeta en todas las terminales concurrentes.

   - Reasignar carrito a otro cliente: PUT /carts/reassignuser con models.GetCartReassingUser { oldUserId: integer, newUserId: integer, uuid: string }.

   FASE 3: Consolidación y Creación del Pedido / Venta:
   - Endpoint: POST /sales/register
   - Request Body: models.GetCartCreateSale
     * companyId (integer, requerido)
     * userId (integer, requerido - ID del Cliente)
     * sellerId (integer, opcional - ID del Empleado vendedor)
     * warehouseId (integer, requerido - ID Bodega)
     * uuid (string, requerido - Mismo UUID de carrito consolidado)
     * saleType (string, opcional - 'sale')
     * paymentMethod (string, opcional - 'cash' | 'transfer' | 'credit')
     * totalAmount (number, opcional)
     * discount (integer, opcional)
     * address (string, opcional), directionId (integer, opcional)
     * invoiceStatus (string, opcional - 'pendiente' o 'facturar' si aplica bypass)
     * reference (string, opcional)
     * saleChannel (string, opcional - 'pos' | 'web')
   - Response: response.APIResponse donde data es models.SaleResponse (saleId, serialCode, invoiceStatus, totalAmount).

5. MÓDULO GESTIÓN CAJA: FACTURACIÓN, HISTORIAL, ARQUEO Y REGLA DE BYPASS POR CRÉDITO
====================================================================================================

5.1. Subítems Consolidados:
   - posBilling      -> Facturación Caja (recaudación multimetodo, verificación y edición de última hora).
   - billingHistory  -> Historial Facturación (reimpresión de tirilla POS 80mm y factura carta; anulación).
   - shiftClose      -> Cierre de Turno (arqueo ciego/guiado contra /payments/summary y cierre de caja).

5.2. Ciclo de Vida del Pedido en Surtido:
   [Pedido Creado: Pendiente (invoiceStatus: 'pendiente')]
             |
             v
   [Caja: Facturación Verificada (invoiceStatus: 'facturar')]  <-- (O Bypass automático por Crédito Sano)
             |
             v
   [Bodega: Picking en Curso (invoiceStatus: 'picking')]
             |
             v
   [Bodega: Picking Verificado (invoiceStatus: 'picking_verified')]
             |
             v
   [Bodega: Packing en Curso (invoiceStatus: 'packing')]
             |
             v
   [Bodega: Packing Verificado / Despachado (invoiceStatus: 'packing_verified')]

5.3. Regla Maestra de Bypass de Caja por Crédito Sano (Contratos Swagger):
   Al crearse un pedido con paymentMethod: 'credit', el frontend o backend evalúa el estado de cartera del cliente mediante models.WalletUser (obtenido de POST /wallet o POST /wallet/summary):
   - models.WalletUser campos evaluados:
     * creditAmount (number): Cupo de crédito total autorizado.
     * reservedCredit (number): Cupo de crédito ocupado/comprometido en órdenes no saldadas.
     * sumAmount (number): Saldo deudor pendiente acumulado.
     * creditDays (integer): Plazo de crédito concedido en días.
     * isCredit (boolean): Bandera que indica si el crédito está activo.

   CONDICIONES OBLIGATORIAS DE BYPASS:
   1. Condición de Cupo Disponible:
      Cupo Disponible = creditAmount - reservedCredit
      (Cupo Disponible / creditAmount) > 0.30  (Dispone de más del 30% de su línea de crédito).
   2. Condición de Días Hábiles:
      creditDaysRemaining >= 20 días hábiles (calculado contra fecha de vencimiento más próxima).
   3. Condición de Saldo en Mora:
      pendingPayments === 0 (no presenta abonos vencidos).

   ACCIONES SEGÚN EVALUACIÓN:
   - Si CUMPLE todas las condiciones: En POST /sales/register se envía directamente invoiceStatus: 'facturar'. El pedido salta la cola del cajero y entra directamente a Bodega para PICKING.
   - Si NO CUMPLE alguna condición: En POST /sales/register se envía invoiceStatus: 'pendiente'. El pedido ingresa obligatoriamente a la pantalla posBilling (Caja) para cobro o autorización manual de sobrecupo.

5.4. Operación en "Facturación Caja":
   - Bandeja de pedidos pendientes: POST /sales/pendings con models.GetPendingsRequest { userId: integer, warehouseId: integer, page, pageSize }.
   - Cobro mediante POST /payments/register:
     * Request Body: models.GetPaymentInsertRequest
       - amount (number, requerido)
       - companyId (integer, requerido)
       - paymentMethod (string, requerido - 'cash' | 'transfer' | 'credit' | 'card')
       - saleId (integer, requerido)
       - userId (integer, requerido - ID del Cliente)
       - userVerifyId (integer, requerido - ID del Cajero auditor en sesión)
       - warehouseId (integer, requerido)
       - reference (string, opcional - Nro de comprobante o autorización bancaria)
       - remainingAmount (number, opcional)
       - status (string, opcional - 'verificado')
   - Aprobación formal del pago: PUT /payments/changestatus con models.GetPaymentChangeStatusRequest { paymentId: integer }.
   - Cambio de estado del pedido a facturado: PUT /sales/status con models.UpdateSaleStatusRequest { saleId: integer, invoiceStatus: 'facturar' }.
   - Anulación de cobro en caso de error: PUT /payments/cancelled con models.GetPaymentCancelledRequest { paymentId: integer, reason: string, userId: integer, isElectronicCancellation?: boolean, electronicCancellationReference?: string }.

5.5. Cierre de Turno y Arqueo de Caja (shiftClose):
   - Endpoint: POST /payments/summary
   - Request Body: models.GetPaymentSummaryRequest
     * companyId (integer, requerido)
     * warehouseId (integer, opcional)
     * startDate (string, opcional)
     * endDate (string, opcional)
   - Response: response.APIResponse donde data es models.PaymentSummaryResponse:
     * totalAmount (number)
     * totalAmountVerified (number)
     * totalAmountPending (number)
     * totalPayments (integer)
     * totalVerifiedPayments (integer)
     * totalPendingPayments (integer)
     * totalCancelledPayments (integer)
     * paymentsByMethod (Array[PaymentMethodSummary]) -> Totales desglosados por 'cash', 'transfer', 'credit'.
   - El cajero ingresa el conteo de efectivo físico (arqueo ciego) y el sistema compara contra totalAmountVerified en efectivo, generando el comprobante de cuadre de caja.

6. MÓDULO TRASLADOS (INVENTARIO): REUBICACIÓN MULTIBODEGA Y CONTROL DE NOVEDADES
====================================================================================================

6.1. Subítems Consolidados de Gestión Inventario (Exactamente 4):

   - La pantalla consulta el producto completo (POST /products con companyId) y extrae locations: Array[models.ProductLocation].

6.3. Ciclo de Vida del Traslado (Alineado con Endpoints Swagger):
   FASE 1: Solicitud de Traslado:
   - Se agregan los repuestos al carrito de traslado: POST /carts/register con:
     { companyId, userId, warehouseId: originId, auxWarehouseId: destId, uuid, productId, price: 0, quantity, typeCart: 'traslade' }.
   - Se formaliza el traslado: POST /sales/register con:
     { companyId, userId, warehouseId: originId, auxWarehouseId: destId, uuid, saleType: 'traslade', invoiceStatus: 'pendiente' }.
   - El backend genera el código único de entrega: serialCode (integer) en models.SaleResponse.

   FASE 2: Consulta de Traslados Entrantes en Destino:
   - Endpoint: POST /sales/traslades
   - Request Body: models.GetTrasladeRequest
     * warehouseId (integer, requerido - Bodega de DESTINO / auxWarehouseId)
     * userId (integer, opcional)
     * page (integer), pageSize (integer)
   - Response: response.APIResponse con Array[models.TrasladeResponse]:
     * saleId (integer)
     * serialCode (integer) -> Código de entrega para verificación física
     * invoiceStatus (string)
     * warehouseInformation (models.WarehouseData - Origen)
     * auxWarehouseInformation (models.WarehouseData - Destino)
     * products (Array[models.SaleItemResponse])
     * userInformation (models.UserData - Operador creador)

   FASE 3: Alistamiento y Empaque en Origen:
   - Al completar picking: PUT /sales/status con { saleId, invoiceStatus: 'picking_verified' }.
   - Al completar empaque: PUT /sales/status con { saleId, invoiceStatus: 'packing_verified' }.

   FASE 4: Recepción y Control de Novedades en Destino:
   - Recepción Exitosa (Sin Novedades):
     Endpoint: POST /sales/approved
     Body: models.GetApprovedTrasladeRequest { saleId: integer, code: integer (código serialCode digitado por el receptor) }.
     Respuesta: models.TrasladeResponse confirmando acreditación de stock en la bodega destino.
   - Rechazo o Novedad (Faltantes / Averías):
     Endpoint: POST /sales/traslades/reject
     Body: models.RejectTrasladeRequest { saleId: integer, reason: string (Detalle de novedades reportadas) }.
     El traslado se marca en la tabla con un badge de advertencia ("Con Novedad") para auditoría de mermas.

7. MÓDULO GESTIÓN ROLES: MATRIZ JERÁRQUICA DE PERMISOS POR EMPLEADO (POST /employees/permissions/modules)
====================================================================================================

7.1. Premisa de Identidad:
   Solo los empleados son usuarios con credenciales en la aplicación ERP. Clientes, proveedores y transportadoras son directorios de datos sin acceso al software.

7.2. Subítems de Gestión Roles:
   - customers        -> Clientes (creación, edición, verificación documental, activación/bloqueo).
   - suppliers        -> Proveedores (mayoristas de repuestos y condiciones comerciales).
   - carriers         -> Transportadoras (directorio logístico de despacho intermunicipal).
   - employees        -> Empleados (ficha laboral interna, sucursal física asignada y cargo).
   - rolesPermissions -> Roles & Permisos (matriz jerárquica de permisos por empleado).

7.3. Estructura Jerárquica del Árbol de Permisos (3 Niveles):
   El esquema de seguridad definido en Swagger opera en 3 niveles complementarios:
   
   NIVEL 1: SEDES FÍSICAS (branches: Array[models.BranchPermissionInfo])
      └── Define a qué bodegas físicas tiene acceso u operación el empleado.
           │
           ▼
   NIVEL 2: MÓDULOS DE NEGOCIO (modules: Array[models.ModulePermission])
      └── [shop | wallet | cashRegister | inventory | thirdParties | reports | settings]
           ├── canRead: boolean   (Visibilidad general del módulo)
           ├── canCreate: boolean (Capacidad de inserción)
           ├── canUpdate: boolean (Capacidad de modificación)
           └── canDelete: boolean (Capacidad de anulación/eliminación)
                │
                ▼
   NIVEL 3: PANTALLAS / SUBÍTEMS (screens: Array[models.ScreenPermission])
      └── Permisos CRUD atómicos para cada pantalla individual del módulo:
           ├── canRead   (Visualización de la tabla / pantalla en SideMenu)
           ├── canCreate (Habilita botones "+ Nuevo", "Crear Traslado", "Crear Pedido")
           ├── canUpdate (Habilita botones "Editar", "Ajustar Precio", "Aprobar Picking")
           └── canDelete (Habilita botones "Anular Factura", "Rechazar Traslado", "Eliminar")

7.4. Reglas Maestras de Visibilidad y Filtrado Dinámico en el Menú Lateral (SideMenu):
   El SideMenu (SideMenu.tsx) lee dinámicamente la configuración asignada por el superadmin:
   - REGLA 1 (OCULTACIÓN TOTAL DE MÓDULO):
     Si el empleado NO tiene ningún permiso de lectura (canRead: false en todas las pantallas del módulo), dicha gestión principal (módulo) NO SE LE PRESENTA en el SideMenu. La opción desaparece por completo del menú para ese usuario.
   - REGLA 2 (APARICIÓN CONDICIONAL CON AL MENOS 1 PERMISO):
     Si el superadministrador habilita AL MENOS UN permiso sobre algún subítem (así sea 1 sola pantalla con canRead: true), la gestión principal SÍ se muestra en el SideMenu, pero desplegando ÚNICA Y EXCLUSIVAMENTE los subítems para los cuales el empleado tiene permiso de lectura (canRead: true). Los subítems no autorizados quedan totalmente invisibles.
   - REGLA 3 (GOBERNANZA DE ACCIONES CRUD EN PANTALLA):
     Dentro de cada pantalla visible, los botones de acción se acondicionan a los flags booleanos del subítem:
     * Si canCreate === false: Se ocultan o inhabilitan botones de creación (+ Nuevo Producto, Crear Traslado, Crear Cliente, etc.).
     * Si canUpdate === false: Se ocultan o inhabilitan botones de edición (Editar, Modificar Carrito, Ajustar Precios, etc.).
     * Si canDelete === false: Se ocultan o inhabilitan opciones destructivas (Anular Factura, Rechazar Traslado, Desactivar Registro).
   - REGLA 4 (PROTECCIÓN DE RUTAS Y REDIRECCIÓN EN MAINCONTENT):
     Si un usuario intenta forzar navegación mediante alteración de URL o estado a un módulo o subítem no autorizado, MainContent.tsx intercepta la petición y renderiza una vista de seguridad ("Acceso Denegado: No posees permisos para visualizar esta sección") o redirige automáticamente al primer subítem autorizado.

9. MOTOR GLOBAL DE VALIDACIÓN Y SANITIZACIÓN DE ENTRADAS (CONTROL DE EXCEPCIONES)
====================================================================================================

9.1. Objetivo:
   Garantizar que todo dato ingresado por el usuario cumpla con los tipos de datos requeridos por la base de datos y Swagger antes del envío, evitando llamadas con error 400/422.

9.2. Utilitario Global: src/global/helpers/validation.helpers.ts
   Funciones puras de validación y sanitización:
   - SANITIZERS.trim(str)            -> Elimina espacios inicio/fin y colapsa espacios dobles internos.
   - SANITIZERS.numericOnly(str)      -> Remueve cualquier carácter no numérico [0-9].
   - SANITIZERS.positiveDecimal(str)  -> Garantiza flotante positivo con un único punto decimal.
   - VALIDATORS.isValidName(str, max) -> Valida longitud (3 a 60 caracteres) y bloquea repeticiones infinitas (regex /(.)\1{4,}/).
   - VALIDATORS.isValidEmail(str)     -> Valida formato RFC 5322 estricto.
   - VALIDATORS.isValidPhone(str)     -> Valida exactamente 10 dígitos celulares (iniciando en 3).
   - VALIDATORS.isValidDocument(str)  -> Valida formato Cédula o NIT (6 a 15 caracteres alfanuméricos).
   - VALIDATORS.isPositiveNumber(num) -> Valida que sea numérico y > 0.

9.3. Verificaciones Asíncronas en Tiempo Real (Debounce 500ms):
   - Correo Duplicado:
     Endpoint: POST /customers/check-email
     Body: models.CheckEmailRequest { companyId: integer, email: string }
     Alerta inmediata: "Este correo ya se encuentra registrado para esta empresa".
   - Documento Duplicado:
     Endpoint: POST /users/validate-document
     Body: models.ValidateDocumentRequest { documentType: string, documentNumber: string }
     Alerta inmediata: "El documento de identidad ya se encuentra registrado en el sistema".

9.4. Componentes Reutilizables:
   - ValidatedInput.tsx (src/global/components/UI/molecules/form/ValidatedInput.tsx):
     Input de texto con contador visual de caracteres restantes (ej. "45/60"), sanitización automática en onChange y mensaje de error con token --color-danger.
   - ValidatedNumberInput.tsx:
     Input para importes y cantidades con bloqueo de teclas no numéricas ('e', 'E', '+', '-', coma) en onKeyDown.

11. TRAZABILIDAD Y AUDITORÍA UNIVERSAL: ESPECIFICACIÓN RIGUROSA DE CONTRATOS API SWAGGER
====================================================================================================

Para garantizar la auditoría total de cada proceso, los endpoints inyectan obligatoriamente los IDs del usuario autenticado:

1. Agregar ítem a Carrito (POST /carts/register):
   - Model: models.GetCartInsertRequest
   - Payload: { companyId: integer, userId: integer, sellerId: integer, warehouseId: integer, uuid: string, productId: integer, price: number, quantity: integer, typeCart: 'sale' | 'traslade', discount?: integer, auxWarehouseId?: integer }
   - Auditoría: Registra el cliente (userId), el vendedor (sellerId) y la bodega de origen.

2. Creación de Pedido / Venta (POST /sales/register):
   - Model: models.GetCartCreateSale
   - Payload: { companyId: integer, userId: integer, sellerId: integer, warehouseId: integer, uuid: string, saleType: 'sale', paymentMethod: 'cash' | 'transfer' | 'credit', totalAmount: number, invoiceStatus: 'pendiente' | 'facturar', ... }
   - Auditoría: Vincula el pedido al vendedor y al carrito unificado por UUID.

3. Cobro en Caja (POST /payments/register):
   - Model: models.GetPaymentInsertRequest
   - Payload: { amount: number, companyId: integer, paymentMethod: string, saleId: integer, userId: integer, userVerifyId: integer, warehouseId: integer, reference?: string }
   - Auditoría: userId registra al cliente y userVerifyId registra al cajero que cobró.

4. Anulación de Venta (POST /sales/cancel):
   - Model: models.CancelSaleRequest
   - Payload: { saleId: integer, userId: integer, reason: string }
   - Auditoría: Registra qué empleado autorizó la anulación y el motivo detallado.

5. Creación de Traslado (POST /sales/register):
   - Model: models.GetCartCreateSale
   - Payload: { companyId: integer, userId: integer, warehouseId: originId, auxWarehouseId: destId, uuid: string, saleType: 'traslade', invoiceStatus: 'pendiente' }
   - Auditoría: userId audita al bodeguero solicitante; warehouseId y auxWarehouseId auditan la ruta del traslado.

6. Aprobación y Recepción de Traslado (POST /sales/approved):
   - Model: models.GetApprovedTrasladeRequest
   - Payload: { saleId: integer, code: integer } (donde code coincide con serialCode)
   - Auditoría: Valida el código de seguridad físico emitido al momento del despacho.

7. Rechazo de Traslado por Novedad (POST /sales/traslades/reject):
   - Model: models.RejectTrasladeRequest
   - Payload: { saleId: integer, reason: string }
   - Auditoría: Registra la no conformidad o faltante en recepción.

8. Asignación de Permisos de Módulos (POST /employees/permissions/modules):
   - Model: models.SaveModulePermissionsRequest
   - Payload: { employeeId: integer, modules: Array<models.ModulePermission> }
   - Auditoría: Actualiza el perfil de permisos granulares del empleado sobre módulos y pantallas.

IP ONLINE - FEATURES BASE
=========================

Proposito
---------
Este archivo documenta el codigo fuente existente en src/features del repositorio importadora-online. Sirve como mapa para seleccionar e integrar capacidades en el proyecto nuevo. No copia ni activa logica de negocio. Los nombres de futuras funciones, endpoints y acciones deben definirse al integrar cada capacidad.

Alcance verificado: 65 directorios de features y 1.030 archivos en el repositorio fuente. El arbol de carpetas se replica como referencia; las pruebas existentes no se trasladan. La descripcion indica la responsabilidad predominante, no garantiza que toda accion de ese modulo este conectada al backend.

NIVELES Y PATRONES
------------------
CLASICO: pantalla, tabla, modal o adaptador de presentacion con pocas capas. Puede consumir datos mock.
INTERMEDIO: varias pantallas/componentes, servicio o interaccion coordinada, pero sin gran estado global propio.
COMPLEJO: estado compartido, multiples operaciones asincronas, flujos por pasos o dependencia amplia entre features.

Patrones mencionados:
- Ruta -> pantalla -> componentes/slots: modulo visible navegable y armado por piezas.
- API -> service -> thunk -> slice -> selector -> UI: flujo de datos con Redux Toolkit.
- Modal por pasos: componente orquestador, mapa de transiciones y pantallas independientes.
- Estado local: estado React del contenedor pasado a sus pantallas mediante props.
- Tabla compuesta: datos transformados en filas y celdas reutilizables.

B. ARBOL DE SRC DEL REPOSITORIO FUENTE
=====================================
La estructura principal a conservar al crear la app nueva es:

src/
  api/                     transporte HTTP, errores, headers y tipos de respuesta
  app/store/               Redux global y hooks tipados
  assets/                  recursos visuales de la aplicacion
  features/                dominios/modulos; ver inventario anterior
  global/                  componentes, layout, helpers, hooks, configuracion y tipos compartidos
  routes/                  router raiz y proteccion de rutas
  services/                servicios transversales (por ejemplo IndexedDB/WebSocket)
  test/                    pruebas y utilidades de prueba del proyecto actual; NO copiar por ahora
  AppInitializer.tsx       inicializacion transversal de la app
  index.css                estilos globales
  main.tsx                 punto de entrada React
  tailwind.config.js       configuracion heredada de estilos
  vite-env.d.ts            tipos de Vite

Capas internas recomendadas para cada nuevo feature, solo cuando sean necesarias:
  api/          llamada HTTP tipada; no contiene JSX ni reglas de presentacion
  services/     adapta/cohesiona acceso a datos y reglas de aplicacion
  thunks/       coordina async, dispatch y lectura de estado cuando usa Redux
  slices/       estado y reducers sin llamadas HTTP
  selectors/    consultas derivadas al RootState
  hooks/        logica reutilizable de React
  screens/      pantallas/composicion de interfaz
  components/   piezas visuales especificas del dominio
  routes/       rutas propias del dominio cuando correspondan
  types/        contratos TS del feature
  helpers/      transformaciones puras y utilidades locales
  strategies/   variaciones de comportamiento intercambiables cuando existe ese caso

No crear todas estas carpetas por plantilla obligatoria: comenzar por la necesidad concreta y evitar capas vacias.

C. REDUX: COMO LEER Y EXTENDER EL STORE
======================================
En el store fuente:
1. Cada slice del feature exporta su reducer.
2. El objeto entregado a combineReducers forma rootReducer. Las claves del objeto son los nombres de state (por ejemplo state.categories), aunque el archivo importado tenga otro nombre.
3. persistReducer(persistConfig, rootReducer) produce persistedReducer. Este wrapper rehidrata/guarda en storage solo las claves de whitelist.
4. configureStore recibe persistedReducer y crea el store con middleware Redux Toolkit.
5. persistStore(store) crea persistor; PersistGate espera la rehidratacion antes de mostrar la interfaz.

Diferencia central:
- combineReducers une reducers; no instala middleware ni hace persistencia.
- rootReducer es el reducer combinado sin persistencia.
- persistedReducer es rootReducer envuelto por redux-persist.
- store es la instancia configurada; persistor administra persistencia.

Whitelist fuente actual: users, user, directionsCart, orderedProducts, shoppingCart. No copiar esta lista automaticamente: cada dato debe justificarse segun sensibilidad, vigencia y necesidad de sobrevivir recargas. La app fuente guarda en localStorage.

Integracion incremental propuesta:
1. Crear/validar el slice dentro del feature autorizado.
2. Importar su reducer en app/store/store.ts.
3. Agregar una clave estable al objeto combineReducers.
4. Actualizar tipos RootState/AppDispatch derivados del store.
5. Agregar la clave a whitelist solo si se decide persistirla.
6. Verificar selector, thunk, Provider y comportamiento de rehidratacion.

No agregar reducers actuales de la aplicacion fuente hasta que se seleccione su funcionalidad. Un reducer importado que no exista en la nueva base hace fallar TypeScript/build.

D. CONTRATO API PARA EL PROYECTO NUEVO
=====================================
Conservar el flujo conceptual de globalApiRequest. El objeto de cada solicitud debe expresar los campos acordados: data, endpoint, method y baseURL. El transporte central debe ocuparse de Axios/HTTP y el feature debe consumir la respuesta tipada a traves de sus capas.

No inventar funciones, endpoints, acciones, slice keys o nombres de dominio en la nueva app. El usuario define los identificadores al seleccionar una capacidad. Las respuestas de API deben tiparse, tratar errores de forma consistente y separar adaptacion de datos de JSX.
